# 固定发布规则

状态：本地规则及程序已更新；新版并行工作流的云端启用与耗时见 `CURRENT_STATUS.md`，不得默认已经启用。

更新时间：2026-09-15。

适用范围：FlightWoodX 每次上传、更新或上线。

替代关系：统一日常发布步骤，替代每轮临时组织命令；不改变质量、授权、备份和回退要求。

## 固定入口

```bash
pnpm release
pnpm release:check
pnpm release --publish
```

- `pnpm release`：只读检查当前版本、正式分支、改动范围及已有 CI，输出发布计划。不提交、不推送、不切换网站。
- `pnpm release:check`：与 `pnpm release` 等价，只读核对已有结果，不重新运行完整本地 CI。两者选一个，不连续执行两遍。
- `pnpm release --publish`：用户已明确要求上线、改动已提交且工作树干净时，执行前端发布。不得用它代替后端、数据库或服务器部署。

开发尚未完成时，先完成当前需求和相关测试。上传代码不等于上线；没有上线授权，不使用 `--publish`。不自动提交未确认文件、不强推、不绕过分支保护。

## 每轮顺序与时间要求

以下为正常网络与运行器可用时的执行目标，不是保证。已有有效证据的普通前端发布目标 **2–5 分钟**；需要新完整 CI 的发布目标 **12–18 分钟**。计算从开始核对到相关线上验收结束的总时间，不只报告上传时间。

| 阶段 | 时间目标 | 必须完成的内容 | 禁止重复的操作 |
| --- | --- | --- | --- |
| 发布前核对 | 1 分钟内 | 授权、工作树、差异、生产祖先、单父历史、证据是否有效；合并任务在启动 CI 前整理完成 | 重新阅读全部历史、反复登录、另开产品审查 |
| 候选检查（仅缺证据时） | 8–12 分钟 | 最终提交完整 CI 一次；一次前端构建，浏览器三普通组加一隐私组独立并行 | 本地完整 CI 后紧接云端完整 CI；每个合并中间版本跑一轮 |
| 上传与切换 | 1–3 分钟，5 分钟告警 | 同一测试归档、完整摘要、已有受限发布器；保留回退版本 | 生产重新构建、重复上传；前端更新重发 API 或操作数据库 |
| 线上验收与收尾 | 1–2 分钟 | 正式版本/入口摘要/健康检查，本次操作一次；如有布局变更补其他尺寸 | 重跑全站业务测试、同一操作在三尺寸重复填写、为写报告再发一版 |

阶段目标不简单相加为承诺。程序默认总等待预算 18 分钟，可显式指定 1–30 分钟；等待到期只停止客户端等待，不取消正在切换的生产作业。CI 超过 12 分钟、部署超过 5 分钟输出一次告警及链接；到期检查同一作业，不重复推送。出现一次明确失败即停止该轮；先修复具体原因，不自动重跑。恢复同一已推送版本只查状态和继续确认，不制造新发布。

需要身份确认、后端/迁移、权限升级、生产事故或运行器长时间排队时，立即报告原因、当前阶段和下一步，不为了符合分钟数省略必要操作，也不得无提示拖延到 40–60 分钟。

## 每次必须遵守

1. **先检查状态。** 一次核对目标仓库、分支、完整提交号、实际文件差异、生产版本和授权范围。身份或权限失败时立即报告，不重复尝试不同登录方式。
   `production` 要求直线历史。跨任务合并先保留原分支，将最终文件整理为基于当前生产提交的单父发布提交并核对内容，再启动候选 CI；程序会提前阻止含合并提交的发布，不能等测试完成后才检查此限制。
2. **先找有效结果。** 同一提交的八项 CI 已成功且测试产物仍有效，直接复用。开发迭代只跑相关测试；最终收尾选择云端完整 CI，或未推送的本地交付执行一次 `pnpm run ci`，不在例行发布前再跑完整本地检查。`pnpm run ci` 已包含 harness，无需另跑。任何代码、依赖或工作流变化产生新提交后，重新取得可信云端证据；本地结果不能替代发布所需的云端归档。权限、网络异常明确失败。
3. **只发布测试过的产物。** 绑定同仓库可信开发分支 push、完整 SHA、CI 运行、产物 ID 和摘要。拒绝其他提交、PR/fork、循环复用、缺项、过期或损坏的证据。生产使用同一归档，不重建后再称已测试。
4. **按范围发布。** 前端变更不重建 API，不操作数据库或权限。后端、共享契约、迁移、依赖、部署程序及无法明确分类的变更单独核验，不能以网页发布成功代表全部完成。
5. **并行但不争用。** 只构建一次前端；三个普通浏览器组加一个隐私组，各有独立 API、数据库和运行器，测试完整覆盖一次。所有组通过才将同一归档标为可发布。保持单组串行、零自动重试；不降低断言或跳过失败。API 镜像检查仍保留一次；前端发布不部署后端，与跳过后端 CI 是两回事。
6. **等待有期限。** 发布程序定时读取准确提交的作业状态，记录各阶段耗时。超过程序上限则报告当前阶段及作业链接，不无限等待或盲目重发；回执不明时先查状态。
7. **最后核对正式站。** 程序检查正式提交、入口文件摘要和 API 健康；人工或既有浏览器用例验证本次实际改动的操作。完整浏览器回归已覆盖且代码未变时，不在生产重复所有写入测试。布局修改在 `390×844`、`768×1024`、`1440×900` 检查布局，完整业务操作只测一次。计划中的范围分类是提示；共享组件、全局样式等影响多个页面时补相关页面，不以分类器代替判断。不新增无关正式账号和数据。
8. **如实收尾。** 报告上线地址、版本、结果、总耗时及异常。不把测试、代码上传、计划或本地预览说成上线。需要回退时使用现有条件回退，不删除旧版本换空间。

## 后端或迁移变更

统一入口会列出它们并停止前端单独发布。按已批准的后端发布方案，先核对环境和持久卷，备份受影响数据，使用验证过的版本，检查兼容性、切换、健康及回退；兼容 API 就绪后再发布依赖它的前端。继续使用已有授权管理通道，不为提速新增通用 SSH、Docker 或数据库权限。

这是当前程序的自动化边界，不表示后端已经支持无人值守的一条命令发布。恢复演练是否可复用必须根据数据结构及恢复方式变化判断，不能只因为时间短就跳过必要备份。

## 耗时与改进

程序保留完整阶段回执；终端仅输出阶段变化、一次超时告警和简短结果。候选 CI 运行中只读作业状态，完成后才读取完整证明；生产推进前再核对一次，保留防止过期或版本竞争的检查。失败只读取对应作业必要的错误片段，不反复读取整段日志和历史任务。

普通发布不搜索网上资料、不重新设计流程、不临时编写多份操作脚本，不为等待调用额外代理。仅在证据异常时检查相关代码。确定性动作交给既有程序，模型负责判断改动范围、异常和验收结果。每轮只维护一份发布记录，其他状态页引用它；没有代码改变，不为补报告再次上线。

2026-09-14 已有证据：实际传输/切换/公网核对 **39 秒**，生产工作流 **91 秒**；三轮候选 CI 约 **34 分钟**。本次优先解决候选重复、双重构建与串行浏览器检查。分组并行可缩短等待，但不承诺减少 GitHub 运行器总分钟数；少读长日志、少重复检查可减少模型用量，具体节省以账单与下一次完整发布计时确认。
